# Project Runner Portfolio Corpus V1

Status: descriptive portfolio cut / not scheduling authority / not effect authority

Observed: 2026-09-24

## Identity

The corpus belongs to **Project Runner**.

Discovery remains the portfolio census and capability-discovery feeder. Project Runner owns the durable descriptive corpus because its job is to connect inventory, currentness, dependencies, scheduling, bounded execution, and completion evidence.

This does not make Project Runner the semantic owner of every project.

## Estate cut

The audited GitHub estate contains 71 repositories:

- 53 public;
- 18 private;
- 69 unarchived;
- 2 archived, both private.

The audit also identified 15 durable non-repository workstreams that should not be double-counted as repositories:

- 2 public;
- 13 private.

The complete private corpus is intentionally external to this public checkout. The public corpus exposes only aggregate private counts. It intentionally does not publish an unkeyed digest of private identifiers.

### P2 — subsystems, specialists, and incubators

P2 contains reusable subsystems, reviewer identities, recovery/repair tools, packaging targets, experimental model-composition systems, and narrow specialist engines.

The governing question for P2 is whether a project has a distinct consumer and measurable responsibility. If it does not, it should donate its useful mechanisms and stop expanding independently.

### P3 — domain, creative, historical

P3 projects are worth preserving and may be active in their own domain, but they do not currently justify portfolio-spine execution bandwidth.

The public cut happens to expose no P3 repository; the complete private corpus contains the domain/creative/history subjects.

### P4 — archived or superseded

The public P4 subject is `build-team-2.0`, which remains useful lineage but is operationally superseded by `bt2`.

The two actually archived repositories are private and therefore appear only in the complete external corpus.

## Repository versus workstream

A major V1 correction is that **repository != project**.

Examples of public cross-repository workstreams are recorded directly in the public corpus:

- The Real Testament of Yeshua: The Man They Called Jesus
- The Nature of Existence

Other private/chat/Drive/runtime workstreams are bound into the complete corpus without forcing creation of another repository.

A workstream may be ACTIVE even when no new repository should exist.

## Corpus versus registry

The corpus is descriptive evidence.

The execution registry is a governed projection.

A P0 corpus record can still be unschedulable. A P4 record can still be read. A current frontier can still lack merge/deploy authority. No priority, activity state, repository membership, or workstream record manufactures authorization.

## Refresh rule

The V1 corpus is an observed cut. Refresh it when:

1. repository membership changes;
2. archive/visibility state changes;
3. a project is superseded or reactivated;
4. a durable non-repository workstream is created, absorbed, completed, or abandoned;
5. a material current frontier changes enough that the existing status becomes misleading.

Mechanical metadata should come from live GitHub/provider evidence. Chat/Drive history may identify durable workstreams or explain lineage, but it does not override fresh source/runtime state.

## V1 next frontier

The next corpus-specific work is not to add another abstraction.

It is to:

1. wire deterministic refresh/diff tooling against the live GitHub estate;
2. compare the public projection against the full external private corpus by count/digest;
3. feed corpus family/priority/activity information into Project Runner as **non-authoritative scheduling context**;
4. require any scheduling decision to re-check exact currentness and existing authority gates;
5. keep Discovery's census synchronized with the same live estate so Discovery and Project Runner cannot silently disagree about what exists.
